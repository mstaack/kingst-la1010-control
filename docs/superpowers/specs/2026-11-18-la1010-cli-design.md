# la1010: CLI for the Kingst LA1010 logic analyzer — design

Date: 2026-11-18
Status: approved in conversation, pending written review

## Goal

A self-contained command-line tool that captures digital signals with a Kingst LA1010 and
decodes UART, I²C, SPI and USB low/full-speed, replacing the vendor GUI (KingstVIS). It must be
easy for humans and for agents: bounded, non-interactive and machine-readable by default.

Non-goals for v1: other Kingst models, PWM output generation, a GUI, USB high-speed decoding,
hardware triggers (the LA1010 has none in streaming mode).

## Verified hardware facts (2026-11-18, user's unit)

Measured with throwaway probes. These are the baseline the driver is built on.

| Item | Value |
|---|---|
| USB ID | `77a1:01a2`, Cypress FX2, no firmware at power-up (bcdDevice 0, no strings) |
| After FX2 upload | re-enumerates as `77a1:01a2`, strings `Kingst` / `Kingst Logic Analyzer`; EP `0x02` bulk OUT, EP `0x86` bulk IN, 512 B |
| Model ID | EEPROM `0x08..0x0f` = `0a f5 00 00 0a f5 10 ef`: magic `0x0a` → LA1010 rev a2. Date at `0x20` = `24 03 db fc` → 2024-03 |
| FPGA | `kingst-la1010a2-fpga.bitstream`, 342 524 B; upload response `0x00` |
| Run register | `0x00e1` idle, `0x00e2` streaming |
| Clock | 800 MHz base, u16 divider (8 → 100 MHz, 80 → 10 MHz) |
| Stream format | u16 LE words, round-robin over enabled channels in ascending order; one word = 16 consecutive samples of one channel; bit 0 = earliest |
| Stop | hardware keeps streaming past the configured sample limit; host must halt |
| Bandwidth | 2 ch × 100 MSa/s (25 MB/s) lossless over 0.67 s; 1 kHz square read back as exactly 50 000 samples per half-period |

Measured during implementation (see `docs/hardware-validation.md`):
- lossless streaming up to 320 Mbit/s (rate × channels); at 400 Mbit/s the device stops and the
  tool exits 2 with "stream stalled"
- 10 s captures at the limit are gap-free

Still not verified:
- channel mapping for CH1–CH15
- accuracy of the threshold voltage
- probe loading on a live USB bus
- cold start (FX2/FPGA upload) by this tool

## Device protocol (from documented behaviour; clean-room, not ported from GPL code)

All control requests are vendor-type on EP0.

| Request | Dir | Use |
|---|---|---|
| `0xA0` wValue=addr | OUT | FX2 RAM write (EZ-USB). `0xE600` = CPUCS: write 1 to hold reset, 0 to run |
| `0xA2` wValue=offset | IN | EEPROM read |
| `0x50` | OUT u32le size / IN u8 | FPGA bitstream upload begin / status (0 = ok) |
| `0x10` wValue=1/0 | OUT | FPGA enable / disable |
| `0x20` wValue=reg | IN/OUT | FPGA register read/write (via SPI) |
| `0x38` | OUT | flush EP6 FIFO |
| `0x30` | OUT | start EP6 bulk data |

FPGA registers used:
- `0x00` run: write 3 = run, 0 = halt; read status, bit 0 = idle
- `0x03` capture mode: 1 = streaming
- `0x04` live pin state (u16)
- `0x10` sample config, 16 B: u40 sample limit, u40 pre-trigger samples = 0, u24 pre-trigger memory = 1, u16 divider, u8 0
- `0x20` channel/trigger config, wIndex = 16: u32 channel mask, three u32 trigger words = 0
- `0x68` threshold: u16 duty R56, u16 duty R79. This formula is the same one sigrok uses; its accuracy on a2 is unverified:
  - V ≥ 2.9: R79 = 0, R56 = 302·V − 363
  - V > −0.4: R79 = 0xF2, R56 = 302·V + 121
  - otherwise: R79 = 0x2D7, R56 = 302·V + 1090
  - R56 clamped to 10..1100; V in ±4.0

Bring-up sequence:
1. If EEPROM read fails, the FX2 has no firmware: set config 1, CPUCS=1, write firmware in 4 KiB chunks from address 0, CPUCS=0.
2. Wait for re-enumeration, polling for up to 3 s.
3. Read the EEPROM magic and map it to a bitstream. Accepted: `0x04` → a0, `0x07` → a1, `0x0a` → a2. Anything else fails with a clear message.
4. Upload the FPGA bitstream unless it is already running (the run register reads idle with bit 0 set). Upload steps: `0x50` OUT size, EP2 bulk in 4 KiB blocks zero-padded to a multiple of 4096, `0x50` IN must return 0, wait 30 ms, `0x10` value 1, wait 40 ms.

Capture sequence:
1. Write threshold, capture mode 1, channel mask, sample config.
2. Flush (`0x38`).
3. Queue bulk IN transfers.
4. Run, then `0x30`, with no pause in between.
5. Read the stream.
6. Halt.

Halting is guaranteed on every exit path: normal end, error and Ctrl-C.

## Firmware handling

The vendor firmware is proprietary and is never committed, embedded or redistributed.

Why: KingstVIS `License.txt` allows free copying and redistribution of the software, but forbids
modifications and grants no rights to individual extracted parts. Users therefore fetch the
firmware from Kingst themselves.

- `la1010 firmware fetch` downloads the official Linux package
  (`https://www.qdkingst.com/download/vis_linux`) over HTTPS into a temporary directory. It
  extracts the files in memory, installs only the LA1010 files and discards the tarball.
  - Extracted files are checked against a built-in table of known-good CRC32/size values from
    v3.6.6.
  - An unknown value, for example from a newer vendor release, produces a warning naming the
    file and value, and the file is still installed.
  - An install whose required files fail to parse exits with code 2.
  - It never runs implicitly. If firmware is missing, every device command exits with code 2 and
    prints the exact `la1010 firmware fetch` command to run.
- `la1010 firmware extract <path>` (offline alternative) accepts a KingstVIS Linux tarball, an extracted directory, or the
  `KingstVIS` ELF binary.
- Extraction steps:
  - parse the ELF symbols `_ZL16qt_resource_data`, `_ZL16qt_resource_name` and `_ZL18qt_resource_struct`
  - walk the Qt rcc tree and inflate zlib-compressed entries (4-byte length prefix)
  - convert Intel-HEX FX2 images into flat binaries
- It writes `kingst-la-01a2.fw` and `kingst-la1010a{0,1,2}-fpga.bitstream`, and prints size and CRC32 for each file.
- Tested against KingstVIS v3.6.6 (SHA-256 of tarball `3fefb141…838fb70`): FX2 5430 B, CRC `720551a9`; a2 bitstream CRC `d2cf8e9e`.
- Lookup order: `--firmware-dir`, `LA1010_FIRMWARE_DIR`, `$XDG_DATA_HOME/la1010`, `~/.local/share/la1010`.
- `fetch` and `extract` both write to the first writable location in that lookup order, or to
  `--out`.

## CLI

Binary `la1010`, crate `la1010`. POSIX style, `--help` with examples on every subcommand.

```
la1010 info [--json]
la1010 firmware fetch [--out DIR]
la1010 firmware extract <path> [--out DIR]
la1010 measure  [-c CH] [-r RATE] [-d DUR] [-t VOLTS] [--json]
la1010 capture  [-c CH] [-r RATE] [-d DUR | -n SAMPLES] [-t VOLTS] [--trigger SPEC] [--pre PCT]
                [-o FILE] [--decode SPEC]... [--json]
la1010 monitor  [-c CH] [-r RATE] [-t VOLTS] --decode SPEC... [--timeout DUR] [--count N]
                [--until TEXT] [--json]
la1010 decode   FILE --decode SPEC... [--json]
la1010 decoders [NAME] [--json]
```

- `-c`: channel list, e.g. `0-3,8`. Default: the channels used by `--decode`, otherwise `0-15`.
- `-r`: rate with SI suffix (`100M`, `24M`, `1k`). Allowed rates are 800 MHz / n, up to 100 MHz. Other values round to the nearest allowed rate and print a stderr note. Default: chosen from the decoders, e.g. USB FS → 100M, UART → ≥16× baud, otherwise 10M.
- `-d`: duration (`500ms`, `2s`). `capture` and `measure` default to 1 s. Nothing runs unbounded without explicit `monitor --timeout 0`.
- `-t`: threshold voltage, default 1.4 V.
- `--trigger`: software trigger, for example `0:rise`, `3:fall`, `0:high,1:low`. `--pre`: pre-trigger percentage of the capture, default 10%.
- `--decode`: `name:key=val,...`. It may be repeated.
- Output files: format chosen by extension, `.vcd`, `.sr` (sigrok session, opens in PulseView and sigrok-cli) or `.csv`.
- A bandwidth warning goes to stderr when rate × channels exceeds the verified lossless limit.

### Decoders

| Name | Options | Emits |
|---|---|---|
| `uart` | `rx=`, `tx=`, `baud=N\|auto`, `bits=5..9`, `parity=n\|e\|o`, `stop=1\|1.5\|2`, `invert` | bytes, framing/parity errors, break |
| `i2c` | `scl=`, `sda=` | start, repeated start, address+R/W, data, ACK/NACK, stop |
| `spi` | `clk=`, `mosi=`, `miso=`, `cs=`, `mode=0..3`, `cs_active=low\|high`, `bits=8`, `order=msb\|lsb` | words (MOSI/MISO pairs) grouped into CS-delimited transfers |
| `usb` | `dp=`, `dm=`, `speed=auto\|fs\|ls`, `show_sof` | bus reset, suspend/resume, packets (PID, addr/ep, payload, CRC5/16 status), transactions, standard SETUP request names |

USB details:
- Line states SE0/J/K are sampled at the bit centre.
- The clock is recovered on each transition.
- Processing is NRZI decode, then bit-unstuffing (a seventh 1 is an error), SYNC, PID with complement check, EOP.
- Speed is detected automatically from the idle polarity: FS when J has D+ high, LS when J has D− high.
- Requires ≥ 4× oversampling (FS ≥ 48 MSa/s; 100 MSa/s recommended).

### Output

Text, one event per line:

```
12.345678ms uart rx 0x41 'A'
12.400100ms i2c  W 0x50 ACK
12.400300ms i2c  data 0x00 ACK
1.000123s   usb  SETUP addr=0 ep=0 → DATA0 [80 06 00 01 00 00 12 00] GET_DESCRIPTOR Device len=18 → ACK
```

With `--json`, the output is NDJSON with one schema:

```json
{"t":0.012345678,"sample":1234567,"proto":"uart","ch":"rx","kind":"byte","value":65,"text":"A"}
{"t":1.000123,"proto":"usb","kind":"transaction","pid":"SETUP","addr":0,"ep":0,"data":"8006000100001200","request":"GET_DESCRIPTOR","handshake":"ACK"}
```

Error events use `"kind":"error"` and carry `"error"`: `framing`, `parity`, `crc5`, `crc16`,
`bitstuff`, or `nack`.

`measure` prints per-channel `edges`, `freq_hz`, `duty`, `min_pulse_s` and `level` (static high or low).

`info --json` prints model, revision, magic, manufacture date, `fx2_loaded`, `fpga_loaded` and the firmware paths.

### Exit codes

| Code | Meaning |
|---|---|
| 0 | ok |
| 1 | usage error |
| 2 | device or firmware error (not found, upload failed, USB error, data overrun) |
| 3 | no result: trigger, `--until` or `--count` not reached within the duration or timeout |

Diagnostics always go to stderr. With `--json`, stderr errors are a single JSON object
`{"error": "...", "code": N}`.

## Architecture

The code is a library crate plus a thin binary. Each module has one job:

| Module | Responsibility | Depends on |
|---|---|---|
| `firmware` | download (fetch), tar.gz reading, Qt-resource extraction from ELF, Intel-HEX, CRC table, file lookup | `ureq` (rustls), `tar`, `object`, `flate2` |
| `device` | discovery, FX2/FPGA bring-up, register I/O, identify | `nusb` |
| `capture` | configure, run, async bulk reads, halt guard, Ctrl-C | `device` |
| `stream` | de-interleave words into per-channel edge lists (`Edge { sample: u64, ch: u8, level: bool }`), software trigger, sample-limit stop | — |
| `decode` | `trait Decoder { fn edges(&mut self, &[Edge], out: &mut Vec<Event>); fn finish(...) }`; `uart`, `i2c`, `spi`, `usb` | `stream` types |
| `measure` | per-channel statistics from edges | `stream` |
| `export` | VCD, sigrok `.sr` (zip: `version`, `metadata`, `logic-1-N` packed samples) and CSV writers; VCD and `.sr` readers for `decode` | `zip` |
| `output` | text and NDJSON rendering of `Event` | `serde_json` |
| `cli` | argument parsing (`clap`), spec parsing, exit codes | everything |

Data flow: bulk IN buffers go to `stream`, which produces edge batches. `capture` sends the batches to
the decoders, `measure` and an optional exporter. Events go to `output`.

Working on edges rather than raw samples keeps memory proportional to signal activity, so long
captures of slow buses stay cheap. It also lets one decoder implementation serve live, file and
test input.

The exporter writes raw samples, so `-o` streams packed samples to disk without keeping them in
memory.

## Error handling

- FX2 does not reappear within 3 s, FPGA status ≠ 0, or an unknown EEPROM magic: exit 2 with the
  observed values.
- USB transfer error or stall during capture: halt the device, flush what was decoded, exit 2.
- Overrun detection: track bytes received against elapsed time. If the device falls behind by more
  than one FIFO's worth, report `overrun` and exit 2, so the output never silently has gaps.
  Whether the FX2 signals overruns some other way is unknown and will be investigated during
  implementation.
- Every exit path, including Ctrl-C, sends halt.

## Testing

- Unit tests:
  - decoders fed synthesised edge streams, including error cases (bad parity, NACK, CRC errors,
    bit-stuff violations, glitches)
  - USB tests from hand-built packets: SETUP/DATA0/ACK, SOF, LS keep-alive
  - CRC5/CRC16 against known vectors
- Format tests:
  - stream de-interleaving against captured `.bin` fixtures from the probe runs (1 kHz square on
    CH0, 1/10/50/100 MHz)
  - VCD and `.sr` write→read round trip
  - firmware extractor tested on a small synthetic ELF built in the test; the vendor binary is not
    a fixture
- Hardware tests are `#[ignore]` and opt-in. Each run needs the user's OK, because they enable the
  RTC1002 pattern generator (`PGEN:FUNC UART|I2C|SPI|SQU`) on P0..P3. Each restores the scope state
  afterwards (`FUNC ARB`, `STIM 8.68e-6`, output off). They cover:
  - channel mapping (requires rewiring P0..P3 to other channels)
  - the bandwidth matrix (1/2/4/8/16 channels × rates) to set the verified lossless limit
  - long-duration continuity
  - decoder checks against the scope's own patterns
- USB decoding on a real bus is a manual step: tap D+/D− of an FS device such as an MCU CDC port
  and compare with known enumeration.
- Run `cargo fmt --check`, `cargo clippy -- -D warnings` and `cargo test` before declaring
  anything done.
